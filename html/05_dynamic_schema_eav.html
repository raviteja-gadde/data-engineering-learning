Dynamic Schema and EAV Patterns

2026-08-23

The Problem: Variable Question Sets

A standard engagement survey has 12 core questions. But real deployments add project-specific custom questions. Project Phoenix runs 12 + 2 custom remote-work questions (14 total). Atlas runs 12 + 5 custom leadership questions (17 total). Orbit runs 12 + 3 custom safety questions (15 total).

This creates a schema problem with no single right answer. Relational databases expect you to declare columns upfront, but the shape of the data varies per project. Four approaches exist, each trading something different off.

Core Tension Schema flexibility vs. query simplicity. The more flexibly you store variable attributes, the harder it becomes to query them analytically. Every approach makes a different bet on this tradeoff.

Four Approaches at a Glance

The same respondent's data -- Q01 score of 4.3 from Project Phoenix, Team Alpha -- is stored completely differently in each approach.

Approach 1: Entity-Attribute-Value (EAV)

EAV -- Entity-Attribute-Value

Mechanism

Decompose every data point into three columns: which entity has the value, which attribute it is, and what the value is. Instead of one column per question, you have one row per question-answer pair.

Adding a new question means inserting rows, not altering the table schema. Zero DDL changes, ever.

Schema

CREATE TABLE eav_responses (
    response_id  INTEGER,
    project      VARCHAR,
    team         VARCHAR,
    attribute    VARCHAR,   -- question identifier (data, not schema)
    value        DOUBLE     -- answer score
);

45 respondents across 3 projects produce 690 EAV rows -- each question-answer pair gets its own row.

Strengths

  • Infinite flexibility. New questions, new projects, new instruments -- just insert rows. No migrations, no DDL.
  • Uniform storage. Easy to backup, replicate, partition by entity.
  • Sparse-data friendly. No wasted columns if projects have different question counts.

Weaknesses

  • Painful analytics. Mean score per question per team requires PIVOT/conditional aggregation.
  • No type enforcement. The value column is one type for everything.
  • AI/text-to-SQL hostile. An LLM must know valid attribute names and construct PIVOT patterns.
The analytical query pain -- see the PIVOT pattern

Computing mean score per question per team in EAV requires one CASE expression per question. For 50 questions, that is 50 repetitive CASE clauses:

SELECT
    team,
    ROUND(AVG(CASE WHEN attribute = 'Q01' THEN value END), 2) AS Q01,
    ROUND(AVG(CASE WHEN attribute = 'Q02' THEN value END), 2) AS Q02,
    ROUND(AVG(CASE WHEN attribute = 'Q03' THEN value END), 2) AS Q03,
    ROUND(AVG(CASE WHEN attribute = 'Q04' THEN value END), 2) AS Q04,
    ROUND(AVG(CASE WHEN attribute = 'Q05' THEN value END), 2) AS Q05,
    ROUND(AVG(CASE WHEN attribute = 'Q06' THEN value END), 2) AS Q06
    -- ... repeat for every question
FROM eav_responses
WHERE project = 'Phoenix'
GROUP BY team ORDER BY team;

Compare to a wide table The same query in a wide table is just AVG(q01_score), AVG(q02_score). No CASE, no conditional aggregation. That is the price EAV charges for its flexibility.
Adding a new question -- zero schema change 
-- Add a brand-new question to Phoenix: zero ALTER TABLE
INSERT INTO eav_responses VALUES
    (9901, 'Phoenix', 'Alpha', 'CNEW01', 4.0),
    (9902, 'Phoenix', 'Beta',  'CNEW01', 3.5);

After insertion, Phoenix now has 15 distinct questions. No table modification, no downtime.

When to use EAV

Systems where schema changes are genuinely unpredictable and frequent, the primary access pattern is entity lookup ("show me respondent X's answers"), and you can afford the analytical query tax. Classic examples: medical records (each patient has different test results), product catalogs (each category has different attributes), CMS field builders.

Approach 2: Slot Mechanism

Slot Mechanism

Mechanism

Pre-allocate a fixed number of generic columns: slot_1, slot_2, ... slot_20. A separate mapping table records what each slot means for each project. The schema never changes; only the mapping data changes.

Schema

-- Response table (fixed width, 20 value columns)
CREATE TABLE slot_responses (
    response_id  INTEGER,
    project      VARCHAR,
    team         VARCHAR,
    slot_1       DOUBLE,
    slot_2       DOUBLE,
    ...
    slot_20      DOUBLE
);

-- Mapping table (the Rosetta Stone)
CREATE TABLE slot_mapping (
    project       VARCHAR,
    slot_number   INTEGER,
    question_id   VARCHAR,
    question_text VARCHAR
);
The slot_13 problem slot_13 means completely different things per project:
  • Phoenix: CRW01 (remote work tools)
  • Atlas: CLD01 (leadership vision)
  • Orbit: CSF01 (physical safety)
The same column holds completely different questions. Without the mapping table, the data is meaningless.

Strengths

  • Deterministic width. Always 20 value columns. Storage is predictable. Query planners work well.
  • Relational aggregation. AVG(slot_1) works like any column.
  • Schema stability. New projects = new mapping rows, not ALTER TABLE.

Weaknesses

  • AI/text-to-SQL cannot reason about "slot_7". Multi-hop reasoning through mapping table is fragile.
  • Slot exhaustion. 20 slots allocated, project needs 25? Schema change.
  • Maintenance burden. Mapping table must be perfectly synced with data loading.
Query: Decoding slots through the mapping table

Every analytical query must join the mapping table and use a massive CASE expression to select the right slot column:

SELECT
    m.question_id,
    m.question_text,
    ROUND(AVG(CASE m.slot_number
        WHEN 1  THEN r.slot_1  WHEN 2  THEN r.slot_2
        WHEN 3  THEN r.slot_3  WHEN 4  THEN r.slot_4
        WHEN 5  THEN r.slot_5  WHEN 6  THEN r.slot_6
        WHEN 7  THEN r.slot_7  WHEN 8  THEN r.slot_8
        WHEN 9  THEN r.slot_9  WHEN 10 THEN r.slot_10
        WHEN 11 THEN r.slot_11 WHEN 12 THEN r.slot_12
        WHEN 13 THEN r.slot_13 WHEN 14 THEN r.slot_14
    END), 2) AS mean_score
FROM slot_responses r
JOIN slot_mapping m ON r.project = m.project
WHERE r.project = 'Phoenix'
GROUP BY m.question_id, m.question_text, m.slot_number
ORDER BY m.slot_number;
AI/Text-to-SQL breakdown An LLM asked "what is the average score for expectations?" must: (1) find "expectations" in slot_mapping, (2) determine it maps to slot_1, (3) query slot_1 from slot_responses, (4) know to filter by project. This multi-hop reasoning is where text-to-SQL fails.

When to use slots

Legacy systems where schema changes are politically or technically expensive (mainframe-era platforms, heavily governed enterprise databases), and the maximum number of attributes is bounded and known.

Approach 3: JSON / Semi-Structured

JSON Column

Mechanism

Store each respondent's answers as a JSON object. The JSON column is schema-on-read: each row can contain a different set of keys. The database does not enforce or know about the keys until query time. Modern analytical databases (DuckDB, Snowflake, BigQuery) support this natively.

Schema

CREATE TABLE json_responses (
    response_id  INTEGER,
    project      VARCHAR,
    team         VARCHAR,
    responses    JSON     -- {"Q01": 4.3, "Q02": 4.0, ..., "CRW01": 4.0}
);

Self-describing data

Each row carries its own question identifiers in the JSON keys. Looking at a sample row tells you exactly what it contains:

-- Response 1 (Phoenix):
{
  "Q01": 4.3, "Q02": 4.0, "Q03": 3.9, "Q04": 3.8,
  "Q05": 4.0, "Q06": 3.3, "Q07": 3.9, "Q08": 3.8,
  "Q09": 3.9, "Q10": 3.2, "Q11": 3.6, "Q12": 4.0,
  "CRW01": 4.0, "CRW02": 3.4
}

Strengths

  • Self-describing. Question identifiers live in the data. Huge for debugging, AI agents, and exploration.
  • Zero-schema-change flexibility. New questions = new keys, no DDL.
  • Natural API fit. Survey responses arrive as JSON from web forms. Skip ETL reshaping.

Weaknesses

  • Verbose query syntax. json_extract(responses, '$.Q01') instead of just q01_score.
  • No column-level statistics. Optimizer cannot build histograms on JSON keys.
  • Repeated type casting. JSON values are strings until you CAST them.
Direct access vs. UNNEST for analytics

Direct access (entity lookup)

-- Pull specific question scores -- no joins needed
SELECT
    response_id, project, team,
    CAST(json_extract(responses, '$.Q01') AS DOUBLE) AS q01,
    CAST(json_extract(responses, '$.Q02') AS DOUBLE) AS q02,
    json_extract(responses, '$.CRW01') AS crw01_or_null
FROM json_responses
WHERE project = 'Phoenix'
LIMIT 5;

CRW01 exists for Phoenix but returns NULL for Atlas/Orbit. No error, no schema issue -- the key simply is not present.

UNNEST for analytics (group-by aggregation)

WITH keys_expanded AS (
    SELECT r.response_id, r.project, r.team, r.responses,
           UNNEST(json_keys(r.responses)) AS question_id
    FROM json_responses r
),
unpacked AS (
    SELECT response_id, project, team, question_id,
           CAST(json_extract(responses, '$.' || question_id) AS DOUBLE) AS score
    FROM keys_expanded
)
SELECT team, question_id,
       ROUND(AVG(score), 2) AS mean_score, COUNT(*) AS n
FROM unpacked
WHERE project = 'Phoenix'
  AND question_id IN ('Q01', 'Q05', 'Q10', 'CRW01')
GROUP BY team, question_id
ORDER BY team, question_id;

Approach 4: Sparse Wide Table

Sparse Wide Table

Mechanism

Give every possible question its own named column. A project that does not use a question simply leaves that column NULL. The opposite bet from EAV: sacrifice flexibility for query simplicity.

Schema

CREATE TABLE wide_responses (
    response_id          INTEGER,
    project              VARCHAR,
    team                 VARCHAR,
    q01_expectations     DECIMAL(2,1),  -- Standard Q12
    q02_materials        DECIMAL(2,1),
    ...
    q12_learn_grow       DECIMAL(2,1),
    crw01_remote_tools   DECIMAL(2,1),  -- Phoenix custom
    crw02_remote_connect DECIMAL(2,1),
    cld01_leadership_vis DECIMAL(2,1),  -- Atlas custom
    ...
    csf03_safety_train   DECIMAL(2,1)   -- Orbit custom
);  -- 22 question columns total

The columnar storage insight

NULLs are free in columnar storage In a row-store (PostgreSQL, MySQL), sparse wide tables incur overhead because every row is stored contiguously -- the engine reads the full row from disk even if most columns are NULL, and the null bitmap grows with column count. In a columnar store (DuckDB, Parquet, Snowflake), NULL columns compress to near-zero bytes. Columnar engines store each column independently and compress NULL runs to negligible overhead. This makes the sparse wide table impractical in OLTP but efficient in analytical databases.

Lab measurement: 22-column wide table in Parquet = 6,250 bytes. Phoenix-only with 14 columns (no NULLs) = 3,211 bytes. The 8 extra mostly-NULL columns add minimal overhead.

Strengths

  • Simplest queries. AVG(q01_expectations) -- no joins, no JSON, no PIVOT.
  • Full optimizer support. Column statistics, predicate pushdown, vectorized execution.
  • AI/text-to-SQL excellent. Column names carry semantic meaning directly.

Weaknesses

  • Schema changes required. New question = ALTER TABLE ADD COLUMN.
  • Column sprawl. Over years, hundreds of columns used by one or two projects.
  • Not truly dynamic. User-generated forms cannot ALTER TABLE fast enough.

Schema metadata: what an AI agent sees 
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'wide_responses'
  AND (column_name LIKE 'q%' OR column_name LIKE 'c%')
ORDER BY ordinal_position;

The AI reads q01_expectations, q05_cares, crw01_remote_tools and immediately knows what to query. No mapping table, no JSON introspection. Column names are the schema documentation.

Decision Framework

The right approach depends on four factors. Walk through each to narrow down your choice.

Storage Engine Matters

Columnar (DuckDB, Snowflake, BigQuery, Parquet)

Sparse wide is cheap. NULLs compress away. This is the storage engine that makes the wide table practical.

Row-store (PostgreSQL, MySQL)

Sparse wide is expensive -- every row stores the NULL slots contiguously. EAV or JSON may be more practical here.

For the Engagement Survey Agent Use Case

Recommendation: Sparse Wide Table
  • Schema variability: LOW -- 12 standard + bounded custom per project
  • Query pattern: ANALYTICS -- mean scores, trends, comparisons
  • Consumer: AI AGENT -- needs semantic column names
  • Engine: COLUMNAR -- NULLs are free in DuckDB/Parquet

Simplest queries, best AI compatibility, negligible NULL overhead. JSON is the reasonable second choice -- self-describing and flexible, but the AI must handle json_extract syntax.
