Frontier Survey Platforms

Multi-Tier Architecture Pattern

Every production survey platform converges on the same multi-tier serving pattern. Raw data flows through transformation tiers (Bronze, Silver, Gold), then gets pushed to a serving layer and cached in memory. The reason is simple: the same data must serve both heavy analytical workloads (regression, NLP, aggregation) and sub-200ms dashboard queries. No single system does both well.

The 500x speedup A query that takes 45 seconds against the analytical layer takes ~90ms from cache. Sub-200ms is the target for core dashboard queries. Every platform in this topic implements some variation of this pipeline.

Qualtrics: The Full-Stack Survey Engine

Qualtrics is the largest dedicated experience management platform, running CX, EX, and market research on the same infrastructure with 20,000+ enterprise customers.

Dynamic Schema at Scale -- fieldsets and the Kafka pipeline

Every Qualtrics survey defines a unique set of questions -- different types (multiple choice, matrix, slider, open-text), different branching logic, different embedded data fields. The platform stores and queries across millions of survey definitions without per-survey schema migrations.

The solution: flattened data schema called fieldsets. Raw incoming data is stored normalized, then transformed into a typed downstream format general-purpose for all analytics. This is conceptually the EAV pattern from Topic 5, but with a critical optimization: fieldsets are pre-typed and pre-flattened for the analytics layer, so queries don't pay the EAV pivot cost at read time.

Pipeline

  • Survey responses submitted over HTTPS
  • Written to short-term response storage
  • Streamed through Kafka to Spark-based transformations
  • Produced as flattened analytical representation in Parquet (columnar -- Topic 2)
  • Hub-and-spoke model: data processed in the hub, surveys available on redundant spokes for HA
Dashboard and Caching Architecture
  • Response Cache -- in-memory cache in front of the response database, serving hot queries
  • Response Database -- persistent analytical store (flattened fieldsets in columnar format)
  • Real-time engine -- Kafka + Spark + fast data stores for streaming dashboards

This maps directly to the pre-computation vs. runtime tradeoff from Topic 4: common dashboard views are pre-aggregated (pre-computation), while ad-hoc slicing falls through to the analytical engine (runtime).

AI Features: Stats iQ, Text iQ, Predict iQ

Stats iQ -- automated test selection

Stats iQ inspects column types and cardinalities, selects the appropriate statistical test, runs it, and translates results into plain language. It is a direct consumer of the typed fieldset schema -- the system knows "this field is a 5-point Likert scale" vs. "this field is a text response" because schema metadata is preserved through the pipeline.

Text iQ -- NLP over open-ended responses

  • 5-level sentiment (Very Negative to Very Positive, plus Mixed)
  • Sentiment intensity (-10 to +10) and polarity (0 to 10)
  • Topic detection: automatic (ML-recommended) and bottom-up (user-defined)
  • Per-topic sentiment scoring -- a single response can have multiple topic sentiments
  • 14+ languages including English, Spanish, German, French, Japanese, Chinese, Korean

Predict iQ -- churn and attrition

  • Builds candidate models using both neural networks and regression
  • Learns from survey responses + embedded operational data (tenure, role, prior scores)
  • Scores new responses as they arrive in real-time
Architectural insight All three iQ features read from the same flattened analytical store. They don't have separate data pipelines -- they're downstream consumers of the fieldset infrastructure, which is why they can operate on any survey without configuration. The schema metadata tells the AI layer what it's looking at.

Culture Amp: People Science + Engineering

Purpose-built for employee engagement and performance. Over 1 billion data points powering benchmarks, running on AWS + GCP. Smaller than Qualtrics but deeply specialized in the people analytics domain.

Confidentiality Architecture -- confidential, not anonymous

Culture Amp draws a careful distinction: surveys are confidential, not anonymous. Every response is tied to an employee record (the system knows who said what), but confidentiality protections prevent anyone from identifying individual responses in reports.

Two protection levels

Basic Protection (default)

If a reporting group has just one participant, the next-smallest group's results are also hidden -- even if that group exceeds the minimum threshold.

Why: prevents inference attacks. If you know the department average and every sub-group except one, you can back-calculate the hidden group.

Strong Protection

Any group with fewer responses than the reporting group minimum is hidden, plus the indirect-identification protection from Basic mode.

Why: handles scenarios where multiple small groups could collectively reveal individual responses through elimination.

This is the same k-anonymity principle from Topic 7, but with the "adjacent group suppression" layer on top that most simple implementations miss. HR administrators can see which feedback traces back to summarized insights (for bias correction), while individual response confidentiality is maintained -- the data-engineering version of role-based access.

Impact -- driver analysis as a product feature

Culture Amp's Impact feature is a productized version of engagement driver analysis. It uses regression-based statistical analysis to answer: "Which survey questions have the most impact on engagement outcomes?"

  • Dependent variable: engagement score (composite of engagement questions)
  • Independent variables: all other survey questions
  • Identifies which questions engaged people are most positive about and disengaged people are most negative about
  • Results ranked by predictive power -- true drivers vs. correlated noise
  • Recalculates dynamically when demographic filters are applied -- different drivers for different teams/locations/tenures
The hard part: filter-aware recalculation This is a direct application of pre-computation + runtime query patterns: the regression model can be pre-fit on the full population (pre-computation), but re-fitting for filtered subgroups happens at query time (runtime). It's not a static report, it's a parameterized model.

Extends to attrition prediction: historical engagement + performance data combined to predict which employees are at risk of leaving, surfacing specific drivers (manager relationship, growth opportunity, recognition) ranked by attrition correlation.

AI-Powered Features (2025+)
  • AI Coach -- conversational interface combining people science with AI for personalized leadership coaching
  • AI-Suggested Improvements -- guides managers in writing actionable, balanced performance feedback
  • AI-Powered Role Comparison -- summarizes job role similarities and transferable skills
  • AI Highlights & Opportunities -- summarizes extensive feedback to identify common themes, minimizing bias in performance discussions
  • Heatmap Explorer -- drill from heatmaps into trends, demographic spreads, and comment analysis
  • Multi-Account Reporting -- unified surveys across entities (the data federation problem)

Medallia: Real-Time Signals at Enterprise Scale

Medallia operates at a different scale point: billions of experience signals across voice, video, digital, IoT, social media, and messaging. Over 1 million weekly AI users. Core differentiator: real-time signal processing and routing.

Signal Processing Architecture -- beyond surveys

Medallia ingests from every touchpoint: surveys, call center recordings, chat logs, web behavior, social media, employee feedback. These are unified through an integration layer connecting operational data (Salesforce, Adobe, ServiceNow) with experience data.

The key architectural difference from survey-only platforms: Medallia treats all inputs as signals, not just survey responses. A call center transcript, a website click path, and a survey response all flow through the same analytical pipeline. This requires:

  • Schema flexibility far beyond fixed survey schemas (Topic 5's EAV/dynamic schema patterns)
  • Real-time processing -- signals analyzed and routed within seconds, not batch-processed overnight
  • Multi-modal analysis -- text, audio, video, structured data all feed the same downstream models
Athena AI Engine
  • Natural Language Understanding -- intent detection without complex setup or constant retraining; models pre-trained on experience data, fine-tuned per deployment
  • Athena Studio -- no-code/low-code platform for building custom AI models; hundreds of pre-built industry-specific models available
  • Intelligent Summaries -- GenAI-powered summarization (multilingual: English, French, German, Spanish)
  • Root Cause Assist -- AI identifies root causes behind experience patterns
  • Smart Response -- automated response generation for customer feedback
Role-Based Access Control -- beyond "who can see what"

Medallia's RBAC is hierarchical and role-specific:

  • Organizational hierarchy defines access rights
  • Role-specific dashboards: frontline employees see immediate customer feedback, managers see team patterns, executives see strategic trends
  • Insights embedded in workflows -- routed to the accountable party automatically
  • Action Plans launched directly from any report, with real-time performance tracking

This is the production version of Topic 7's row-level security patterns, with the addition of workflow routing: suppression and access control aren't just about hiding data, they're about showing the right data to the right person at the right time and prompting action.

Common Patterns Across All Three

Despite different market positions and scale points, these platforms converge on the same architectural patterns. This convergence is the signal -- these aren't arbitrary design choices, they're solutions forced by the problem domain.

1. Dynamic Schemas with Pre-Typed Analytics

Store raw data flexibly (EAV-like or document-oriented), then transform into a typed, flattened analytical representation. Schema metadata travels with the data so downstream systems know what they're working with.

Topic 5 (EAV flexibility) + Topic 3 (medallion transformation)

2. Multi-Tier Serving with Cache

Cache <1ms in-memory for repeat queries. Serving <50ms pre-aggregated tables. Analytical: seconds columnar store for ad-hoc.

Topic 4's pre-computation hierarchy with real caching infrastructure

3. AI as Downstream Consumer

None run AI on separate data copies. Stats iQ, Impact, Athena all read from the same analytical store. Schema metadata (type, scale, question text) flows through the pipeline so AI features work on any survey without per-survey configuration.

Data model must serve both human dashboards and ML models

4. Suppression as First-Class Concern

  • Basic: hide groups below a count threshold (Topic 7 baseline)
  • Adjacent group: hide the next-smallest group to prevent inference (Culture Amp)
  • Role-aware: different thresholds for different user roles (Medallia)
  • Dynamic: computed per query, never pre-flagged on rows

5. Analytical / Serving Separation

Analytical engine for heavy computation (aggregation, regression, NLP). Serving layer for interactive dashboards and APIs. Pre-computed aggregates bridge them.

Implications for Your Design

Where You're Already Adequate

The architecture from Topics 1-7 covers the structural foundations:

  • Star schema (Topic 1) -- core fact + dimension model
  • Columnar storage (Topic 2) -- analytical query performance
  • Medallion pipeline (Topic 3) -- raw-to-analytics transformation
  • Pre-computation (Topic 4) -- common dashboard cuts
  • Dynamic schema (Topic 5) -- question flexibility
  • OLTP/OLAP separation (Topic 6) -- analytical vs. serving split
  • Suppression (Topic 7) -- privacy and group-size constraints

Where These Platforms Go Further

Multi-Tier Cache

The architecture so far pre-computes to serving tables but doesn't implement an in-memory cache layer. For an AI agent use case: cache the most common tool call results in memory, fall back to pre-computed tables, fall back to analytical queries.

Schema Metadata in Pipeline

The fieldset / typed-schema approach means AI features get column semantics for free. The AI agent needs to understand what Q01-Q12 mean -- that metadata should flow through the pipeline, not be hardcoded in the agent's prompts.

Dynamic Driver Analysis

Culture Amp's Impact feature (regression re-computed per filter) is a pattern the agent could implement: given a filtered population, which questions are most predictive of engagement? Requires parameterized regression, not just pre-computed averages.

Real-Time Routing

Medallia's signal-to-action loop (detect pattern, route to owner, track action) represents where survey analytics eventually goes -- from "show me the data" to "tell the right person what to do."

Where to Focus Engineering Effort

  1. Cache layer -- add in-memory caching to the serving path; highest ROI for response time
  2. Schema metadata -- ensure question semantics (text, type, scale, category) are available to the AI agent without hardcoding
  3. Parameterized aggregation -- support filter-aware pre-computation so the agent can answer "what drives engagement for Team X" without a full table scan
  4. Adjacent-group suppression -- upgrade from simple threshold suppression to Culture Amp's inference-prevention model
