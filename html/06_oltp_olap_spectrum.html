The OLTP / OLAP Spectrum

Every database is optimized for one of two workload patterns. Understanding which you're dealing with — and when to use each — is the single most important architectural decision in data engineering.

OLTP: Online Transaction Processing

Serves your application. A user submits a survey response: INSERT one row. The app fetches an employee profile: SELECT one row by primary key.

  • Many small, fast operations — thousands per second
  • Touches few rows — usually 1-10 per query
  • Reads and writes interleaved — same table gets INSERTs while other connections SELECT
  • ACID required — concurrent submissions must not corrupt each other
  • Latency <10ms

Survey domain: the application DB where individual Q12 responses are stored as users submit them.

OLAP: Online Analytical Processing

Answers analytical questions. "Mean engagement score by department for Q1 2025?" — scans hundreds of thousands of rows, joins dimensions, groups, aggregates.

  • Few complex queries — tens to hundreds per day
  • Scans massive row ranges — full-table scans are normal
  • Mostly reads — periodic bulk writes (batch loads)
  • Eventual consistency OK — yesterday's data is fine
  • Latency: seconds to minutes

Survey domain: the warehouse computing engagement trends by department over 8 quarters across 500K+ rows.

Engine Architecture: PostgreSQL vs DuckDB

The two engines spend their optimization budget on fundamentally different things.

Key Insight Running an OLAP query on an OLTP engine works but wastes resources — PostgreSQL reads entire rows from disk even if you only need 2 columns. Running OLTP workloads on an OLAP engine works but lacks concurrency primitives. Neither is "better" — they're different tools optimized for different access patterns.

Why DuckDB "Wins" OLTP Here DuckDB runs in-process (no network hop) while PostgreSQL is accessed over a TCP socket. This benchmark compares apples to oranges for OLTP workloads. At production scale with concurrent users, PostgreSQL's B-tree indexes, row-level locking, and MVCC give it the OLTP advantage DuckDB cannot match. Lab 01 Code: Benchmarking Both Engines 
# Same query, both engines:
def bench_pg(sql, params=None, runs=10):
    times, result = [], None
    with pg_conn() as pg:
        cur = pg.cursor()
        for _ in range(runs):
            s = time.perf_counter()
            cur.execute(sql, params)
            result = cur.fetchall()
            times.append((time.perf_counter() - s) * 1000)
    return sum(times) / len(times)

# OLAP query: 3-way JOIN + GROUP BY + AVG

GROUP BY q.category ORDER BY q.category"""

The Serving Layer Pattern

The most practically important pattern in this topic. Your analytics warehouse can answer any question — but queries take 5-30 seconds. Your dashboard / AI agent / API endpoint needs answers in <100ms. The solution: separate computation from serving.

Why This Works: Volume Mismatch

Raw data: 48,000 rows. Aggregated result: 200 rows. Reading 200 pre-computed rows by index is trivially fast on any engine. The expensive computation already happened offline.

The Survey Data Case

  • Overview screen (get_team_overview): serving layer problem. Pre-compute in DuckDB, push to PostgreSQL, serve by team_id. User sees results in <100ms.
  • Drill-down screen (get_drill_down): possibly a runtime OLAP problem. Too many dimension combinations to pre-compute all of them. Options: accept 2-5s latency, use embedded DuckDB for <1s response, or pre-compute common paths and fall back to runtime for rare ones.
This is how analytics SaaS works Looker caches query results. Sigma sends live queries but caches aggressively. Hex materializes datasets during notebook runs. Mode caches results in application storage. None of them make the user wait 15 seconds for every dashboard view. They all use compute-once-serve-many.
Lab 02 Code: The Three-Stage Pipeline 
# Stage 1: Compute in DuckDB (OLAP)
gold_sql = """SELECT t.team_id, t.name, t.department, q.category,
       ROUND(AVG(r.score), 2), COUNT(*)
FROM responses r
JOIN teams t ON r.team_id = t.team_id
JOIN questions q ON r.question_id = q.q_id
GROUP BY t.team_id, t.name, t.department, q.category"""
gold_rows = duck.execute(gold_sql).fetchall()  # 3.11ms

# Stage 2: Push to PostgreSQL (OLTP)
cur.execute("""CREATE TABLE gold_serving (
    team_id INT, team_name VARCHAR, department VARCHAR,
    category VARCHAR, mean_score NUMERIC(4,2), n INT,
    PRIMARY KEY (team_id, category))""")
cur.execute("CREATE INDEX idx_gold_team ON gold_serving (team_id)")
for row in gold_rows:
    cur.execute("INSERT INTO gold_serving VALUES (%s,%s,%s,%s,%s,%s)", row)

# Stage 3: Serve from PostgreSQL (point lookups)
cur.execute("SELECT * FROM gold_serving WHERE team_id = %s", (42,))
# 0.34ms — B-tree index lookup

PostgreSQL as a Hybrid Engine

PostgreSQL can handle light analytics via materialized views — pre-computed aggregations stored as tables, refreshed on demand. Lab 03 tests whether you can avoid a separate OLAP engine entirely.

Lab 03 Results: 9,000 Rows (15 teams x 12 questions x 50 respondents)

OperationLatency
INSERT 1 response0.302 ms
UPDATE 1 response0.247 ms
DELETE 1 response0.259 ms
ApproachQuery LatencyBuild Cost
Runtime aggregation5.00 ms0 (computed on demand)
Materialized view0.42 ms6.2 ms (one-time)

The materialized view is 12x faster to query than runtime aggregation. But it has a cost: staleness.

The Staleness Problem

SourceBasic Needs MeanStatus
Materialized View3.98STALE — doesn't see new data
Runtime Query4.27FRESH — always current

After inserting 240 new responses (all score=5.0), the materialized view still returns the old mean. REFRESH MATERIALIZED VIEW costs 6.5ms at 9K rows — fast enough. At 100M rows, refresh can take minutes and blocks reads (unless you use REFRESH MATERIALIZED VIEW CONCURRENTLY).

When Is Hybrid "Good Enough"? PostgreSQL + materialized views works when ALL of these hold:
  1. Dataset <10M rows — MV refresh takes seconds, not minutes
  2. Staleness is acceptable — surveys update quarterly; hourly/daily refresh is fine
  3. Query patterns are predictable — you know which aggregations to materialize
  4. No heavy concurrent analytical load — a few dashboard queries per minute
When you outgrow any of these: move analytical workload to DuckDB/Snowflake.
Lab 03 Code: Materialized View Lifecycle 
# Create the materialized view
cur.execute("""CREATE MATERIALIZED VIEW mv_team_scores AS
    SELECT t.team_id, t.name, t.department, q.category,
           ROUND(AVG(r.score)::numeric, 2) AS mean_score,
           COUNT(*) AS response_count
    FROM survey_responses r
    JOIN survey_teams t ON r.team_id = t.team_id
    JOIN survey_questions q ON r.question_id = q.q_id
    GROUP BY t.team_id, t.name, t.department, q.category""")
cur.execute("CREATE INDEX idx_mv_team ON mv_team_scores (team_id)")

# Query the MV: 0.42ms (vs 5.00ms runtime)
cur.execute("SELECT * FROM mv_team_scores ORDER BY team_name, category")

# After new data arrives... MV is STALE
# Fix: REFRESH (re-runs full query)
cur.execute("REFRESH MATERIALIZED VIEW mv_team_scores")  # 6.5ms at 9K rows

The Blurring Spectrum

The clean OLTP/OLAP split is a useful mental model, but several forces are pushing engines toward each other.

DuckDB: Embedded OLAP

SQLite for analytics. Runs in-process, no server. Columnar engine with vectorized execution, compression, parallel scans — all in a library.

  • Use case: local analytics, pipeline transforms, embedded app dashboards
  • Limitation: no row-level locking, no concurrent write transactions, no replication

PostgreSQL + Extensions

OLTP reaching toward OLAP with parallel query (v9.6+), partitioning (v10+), materialized views, BRIN indexes, and columnar extensions (Citus/Hydra).

  • Still: fundamentally row-oriented at the storage layer
  • Good for: small-medium datasets (<10M rows) where you want one engine

Snowflake Hybrid Tables

OLAP reaching toward OLTP. ACID transactions, unique constraints, foreign keys, single-digit ms point lookups — inside a columnar warehouse.

  • Catch: expensive. Warehouse compute prices for workloads PostgreSQL handles cheaply.

Real-Time OLAP

ClickHouse, Apache Pinot, Apache Druid: high-throughput writes (100K+ events/sec) + sub-second analytical queries.

  • ClickHouse: columnar, append-optimized. Observability.
  • Pinot: real-time ingestion from Kafka. LinkedIn's analytics.
  • Not: general-purpose OLTP — no row-level updates, no general transactions.

When to Use What

CategoryEngine(s)Use When
Pure OLTP PostgreSQL, MySQL App database (auth, forms, CRUD). Serving layer for pre-computed results.
Pure OLAP Snowflake, BigQuery, Redshift Warehouse. Batch computation, historical analysis, complex joins over large datasets.
Embedded OLAP DuckDB Local dev/test. Pipeline transforms. App-embedded drill-downs that need sub-second latency.
Hybrid / Real-time OLAP ClickHouse, Pinot, Druid High-volume event ingestion + low-latency dashboards. Observability, real-time analytics.
PG as "good enough" hybrid PostgreSQL + materialized views <10M rows, predictable query patterns, staleness acceptable, no heavy concurrent analytics.
