Physical Layout: Row vs Column

Every database stores data in pages (typically 4-8 KB blocks on disk). The difference between row-oriented and column-oriented storage is what goes into each page. This is not an abstraction — it determines which disk blocks the OS reads when you run a query.

The core insight For SELECT AVG(q01) FROM responses, row storage reads every page in the table because q01 is scattered across all pages alongside name, team_id, q02-q12. If the table has 15 columns, roughly 14/15 of the data read from disk is thrown away. Column storage reads only the pages containing the q01 column — 1/15th of the I/O.

For OLTP workloads — SELECT * FROM responses WHERE id = 42 — row storage wins. The entire row lives in one page. Column storage must fetch one page per column and reassemble them, which is slower for point lookups.

Three Stacking Advantages

Three reinforcing advantages stack on top of each other, compounding into the large speedups seen in analytical workloads.

1. Column Pruning

Read only the columns the query references. A dashboard query computing AVG(q01) grouped by team_id touches 2 columns out of 50+ in a real survey table.

This is typically the largest contributor to speedup on wide tables.

2. Better Compression

Same-type, similar-value data compresses dramatically better. team_id values are all short strings from a small set. q01 values are all integers 1-5.

Compression ratios of 5-10x are common for columnar vs 2-3x for row storage.

3. Vectorized / SIMD

A contiguous array of q01 integer values can be processed in CPU-native SIMD batches of 2048 values, sized to fit in the L2 cache (~256 KB).

Row storage interleaves different types, breaking the pattern SIMD needs.

Compression Techniques

Columnar engines choose compression per-column based on data characteristics. The engine inspects statistics (cardinality, value distribution, type) and picks the best technique automatically.

Run-Length Encoding (RLE)

Replace consecutive identical values with (value, count) pairs. Works best on low-cardinality columns — especially when sorted.

Dictionary Encoding

Replace string values with integer codes, store the dictionary separately. Beyond storage savings, integer comparisons are faster than string comparisons, so WHERE department = 'Engineering' becomes WHERE dept_code = 0 internally.

// Dictionary: {0: "Engineering", 1: "Sales", 2: "Product"}
// Raw:        ["Engineering", "Sales", "Engineering", "Product", "Engineering"]
// Encoded:    [0, 1, 0, 2, 0]  ← integers instead of strings

Delta Encoding

Store the first value and then differences from each predecessor. The deltas are small numbers that compress well with further encoding. Works best on sorted or naturally sequential columns — timestamps, auto-increment IDs, dates.

// Timestamps: [1000, 1001, 1002, 1005, 1006]
// Delta:      [1000, +1,   +1,   +3,   +1]  ← small numbers compress well

How They Combine

Real columnar engines layer these techniques. A survey_date column might be delta-encoded (dates become small offsets), then bit-packed (small numbers need fewer bits), then optionally RLE'd if consecutive deltas are identical. The engine chooses automatically based on data statistics.

Why NULLs Are Free in Columnar Storage

The insight that changes how you think about sparse survey data A column that is 95% NULL compresses to near-zero storage. The NULL runs collapse: [(NULL, 950), (4, 1), (NULL, 12), (3, 1), ...]. In the lab, a 95% NULL column used only 1.3% of total table storage — 49.7 KB out of 3.6 MB.

This challenges the common concern about "ever-widening tables" in survey data. Adding 20 custom questions that only 5% of respondents answer barely affects storage or query performance in a columnar warehouse. The NULLs compress away. In row storage, those 20 extra columns bloat every page whether they contain data or not.

Predicate Pushdown & Late Materialization

Predicate Pushdown

"Push the WHERE clause down to the storage layer" — filter rows before they leave disk, rather than reading everything and filtering in memory.

clustering keys: physically organize data by the columns you filter most. Also called zone maps: store min/max per block, skip entire blocks based on WHERE clause.

Late Materialization

Traditional query processing reads all columns for matching rows, then evaluates expressions. Late materialization reads only the column(s) needed for the WHERE clause first, identifies which row positions match, then reads the other columns only for those positions.

-- SELECT name, q01, q02 FROM responses WHERE team_id = 'Engineering'
--
-- Step 1: Scan ONLY team_id column → positions [0, 1, 2, 5, 8, ...]
-- Step 2: Read name, q01, q02 ONLY at those positions
-- Step 3: If WHERE eliminates 80% of rows, you avoided reading
--         80% of the other columns
--
-- This compounds with column pruning: fewer columns AND fewer values per column.

Snowflake Micro-Partitions

Snowflake stores data in micro-partitions: immutable chunks of 50-150 MB, internally columnar and compressed.

Immutable

Updates and deletes create new micro-partitions; old ones are garbage-collected. No in-place modification — this avoids the recompress-on-write problem.

Automatic

You don't manage partitions. Snowflake decides how to split data based on ingestion order.

Min/Max Pruning

Each micro-partition stores min/max of every column. WHERE survey_date = '2025-Q1' can skip partitions whose date range doesn't include Q1 2025.

Clustering Keys

CLUSTER BY (team_id) physically reorganizes micro-partitions so rows with similar values land together. Maximizes pruning effectiveness.

Analogy: Micro-partitions are like chapters in a book, and min/max metadata is like the index at the back. Instead of reading every page to find "Chapter 7," you check the index and jump directly to it.

Vectorized Execution

Traditional row-at-a-time processing (the Volcano model): each operator processes one row, calls the next operator for one row, producing a function call per row per operator. For millions of rows, the overhead is enormous.

Vectorized execution processes a batch of values (DuckDB uses ~2048). The batch is a contiguous array of one column's values. Why 2048? DuckDB sizes batches to fit in the CPU's L2 cache (~256 KB). A batch of 2048 int32 values is 8 KB. Multiple columns' batches fit in L2 simultaneously — data stays in fast cache memory throughout processing.

Why the differences?
  • Python for-loop: Each iteration pays bytecode dispatch, type checking, float box/unbox, branch prediction miss. Tens of nanoseconds per element × 10M elements.
  • pandas: Wraps the numpy array (zero-copy), then compiled C loop. Small overhead from Series construction.
  • NumPy: Compiled C with SIMD intrinsics. Processes 4-8 doubles per CPU cycle. Minimal overhead.
  • DuckDB SQL: Vectorized execution with ~2048-value batches sized for L2 cache. Uses SIMD internally. Small overhead from SQL parsing and query engine pipeline, but nearly matches NumPy on a single AVG().

The lesson: analytical query engines are fast because they use the same techniques as NumPy (compiled code, SIMD, cache-aware batching) but applied to SQL queries over arbitrary schemas.

What Columnar Does NOT Solve

Columnar storage is not a silver bullet It optimizes data access patterns for analytical queries, but does not fix every data problem.
  • Schema design still matters. A poorly designed star schema in a columnar warehouse is still slow. Columnar doesn't fix bad grain decisions or missing dimensions.
  • Terrible for OLTP. Inserting one survey response requires updating every column's storage separately. Point lookups (WHERE id = 42) require reassembling columns. Don't use columnar as a primary store for production applications.
  • Clustering/sort key choices matter. Predicate pushdown only helps if data is physically organized for skipping. Random layout gets no pruning benefit.
  • Not a replacement for all indexing. Columnar pruning works on ranges and equality. Complex predicates (full-text search, spatial queries) still need specialized indexes.
  • Compression can backfire for updates. Compressed blocks must be decompressed, modified, and recompressed. This is why Snowflake uses immutable micro-partitions instead of in-place updates.
