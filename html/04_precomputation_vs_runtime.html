Pre-Computation vs Runtime Computation

2026-08-23

The Fundamental Tradeoff

Every data system answers the same question differently: when do you compute?

Given a query — "show me mean engagement score by team for Q1 2025" — there are two paths:

Runtime Computation

Run the full aggregation query when the user asks. Joins fact table to dimensions, scans all matching rows, computes AVG.

Pro: Always returns the freshest data.

Con: Latency and compute cost on every request.

Pre-Computation

Run the query once, store the result in a table. When the user asks, scan the pre-computed table — no joins, no aggregation.

Pro: Fast reads, minimal compute per request.

Con: Storage, staleness, rebuild complexity.

This isn't a "pick one" decision. Real systems use a spectrum of strategies based on three variables:

  • Latency requirement. A dashboard overview card needs sub-100ms. An ad-hoc drill-down can tolerate 5–15 seconds.
  • Data freshness requirement. Financial dashboards need real-time. Engagement surveys update quarterly — hours of staleness is fine.
  • Query predictability. If you know the exact queries (e.g. "team x period"), you can pre-compute. If users can slice by any combination of 8 dimensions, you can't pre-compute them all.

The Pre-Computation Pipeline

Pre-computation moves work from query time to build time. The pipeline has clear stages:

Aggregation Strategies

Full Pre-Computation: The OLAP Cube

The theoretical extreme — pre-compute every possible combination of dimensions. For survey data with 6 dimensions (team, question, time_period, department, location, category), the cube contains a cell for every combination.

Works when dimension cardinalities are small and dimensions are few (3-4). Breaks when dimensions multiply — the combinatorial explosion problem.

Partial Pre-Computation: Rollup Tables

Identify the hot paths — the 2–3 dimension combos covering ~80% of actual queries — and pre-compute only those.

Rollup TableDimensionsCoversRows
rollup_team_periodteam x time_periodOverview card160
rollup_dept_categorydepartment x categoryDept comparison view20
rollup_team_category_periodteam x category x time_periodTeam detail page640

Everything else — ad-hoc slicing, uncommon dimension combos — is computed at runtime against the fact table.

How to pick rollup dimensions Instrument your queries. Log which dimensions users actually GROUP BY and filter on. The top 2–3 combos dominate. This is the 80/20 rule applied to query patterns.

Full Runtime Computation

No pre-computation at all. Every query hits the fact table directly. Simplest architecture — no rollup tables to maintain, no staleness, no rebuild pipelines.

Works when a columnar engine (DuckDB) handles the data volume acceptably. Breaks at millions of rows with multi-table joins, concurrent users, and "instant" latency requirements.

Combinatorial Explosion

This is the core reason you can't "just pre-compute everything." Each new dimension multiplies the row count — it's not additive.

How Dimensions Multiply

Rollup Tables: SUM + COUNT, Not AVG

You can't average averages If Team A has AVG=3.5 (n=100) and Team B has AVG=4.0 (n=50), the combined average is NOT (3.5+4.0)/2 = 3.75. It's (350+200)/150 = 3.67. You need SUM and COUNT to combine correctly.

Lab Result: SUM + COUNT rollup in action

From 01_precompute_vs_runtime.py — the rollup stores SUM and COUNT, then derives AVG at query time:

SQL
-- Build rollup: store SUM + COUNT, not AVG
CREATE TABLE rollup_team_category_period AS
SELECT dt.team_name, dt.department, dq.category, dp.period_label,
       SUM(f.score) AS sum_score, COUNT(*) AS n
FROM fact_responses f
JOIN dim_team dt     ON f.team_key = dt.team_key
JOIN dim_question dq ON f.question_key = dq.question_key
JOIN dim_period dp   ON f.period_key = dp.period_key
GROUP BY dt.team_name, dt.department, dq.category, dp.period_label;

-- Query rollup: derive AVG from SUM/COUNT
SELECT team_name, department, category, period_label,
       ROUND(sum_score * 1.0 / n, 2) AS mean_score, n
FROM rollup_team_category_period
ORDER BY team_name, period_label, category;

The Serving Layer Pattern

This is the pattern that makes analytics SaaS products feel fast. It separates computation from serving:

Why Two Stores?

OLAP Engines

DuckDB, BigQuery, Snowflake

  • Built for scanning millions of rows
  • Joining large tables, computing aggregates
  • Bad at: thousands of concurrent point lookups with sub-ms latency

Transactional Stores

PostgreSQL, Redis, DynamoDB

  • Built for concurrent point lookups
  • WHERE team_key = 42 with indexing
  • Bad at: scanning and joining large analytical tables

Caching: Pre-Computation with an Expiration Date

Caching is pre-computation with a TTL. Instead of permanent rollup tables, results live in a fast-access layer (memory, Redis, application dict) and expire.

Cache States

Fresh Hit

Fast + Correct

Best case. Cached result matches what a live query would return.

Stale Hit

Fast + WRONG

Dangerous — invisible. Cache returns confidently, nobody knows it's wrong until they compare.

Miss

Slow + Correct

Cache expired or never existed. Falls back to expensive query, gets right answer, populates cache.

Beyond TTL

  • Event-driven invalidation. When new data loads, explicitly clear the cache. No stale window. More complex — the write path must know about the cache.
  • Versioned keys. Include a data version in the cache key: team_scores_v17. Increment on data change. Old keys naturally expire.
  • Write-through. Update cache and database together. Always fresh. Cost: every write is slower.
For survey data Event-driven invalidation is the natural fit. Surveys close on a known schedule. ETL runs, loads data, invalidates cache. Between surveys, the cache never goes stale because the data doesn't change.

The Freshness-Latency Spectrum

Every point on this spectrum is a valid design choice. The right one depends on your domain:

Strategy Comparison

Strategy Latency Freshness Complexity Best For
Full runtime 1–15s Always fresh Low Ad-hoc queries, small datasets
Cache + TTL ~0ms repeat Stale window Low–Medium Repeat queries, tolerable staleness
Rollup table ~1ms Stale until rebuild Medium Predictable queries, hot paths
Serving layer <0.5ms Stale until push High Dashboard overview, concurrent users
OLAP cube ~0ms lookup Stale until rebuild Very high Few dimensions, small cardinalities

TTL cache implementation (Python) 
Python
class TTLCache:
    """Minimal cache: key -> (value, expiry_time)."""

    def __init__(self, ttl_seconds: float):
        self.ttl = ttl_seconds
        self._store: dict = {}
        self.stats = {"hits": 0, "misses": 0}

    def get(self, key: str):
        if key in self._store:
            value, expiry = self._store[key]
            if time.time() < expiry:
                self.stats["hits"] += 1
                return value, "HIT"
            else:
                del self._store[key]
                self.stats["misses"] += 1
                return None, "EXPIRED"
        self.stats["misses"] += 1
        return None, "MISS"

    def put(self, key: str, value):
        self._store[key] = (value, time.time() + self.ttl)

Key Takeaways

  1. Pre-computation trades freshness for speed. The question is always "when do you compute?" — at query time or before?
  2. Combinatorial explosion makes full pre-computation infeasible beyond ~4-5 dimensions. Each dimension multiplies storage, not adds.
  3. Store SUM + COUNT, not AVG. You can always derive AVG from SUM/COUNT. You can't average averages correctly.
  4. The serving layer pattern (OLAP compute → push to transactional store → serve) is how analytics SaaS achieves sub-100ms dashboards.
  5. Caching has three states: fresh hit (fast + correct), stale hit (fast + wrong), and miss (slow + correct). The stale hit is the dangerous one because it's invisible.
  6. Real systems use multiple strategies matched to access patterns: pre-compute the overview, cache repeat queries, runtime for ad-hoc.
