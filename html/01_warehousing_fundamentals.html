Warehousing Fundamentals

2026-08-23

A data warehouse is a separate database optimized for analytical queries -- the opposite of your transactional (OLTP) application database. While your app handles thousands of small, fast reads and writes per second, a warehouse handles a few massive queries that scan millions of rows to produce aggregated insights.

OLTP (App Database)

  • Read one employee, insert one response
  • Normalized schema (3NF), foreign keys
  • Current-state only
  • Single source system

OLAP (Data Warehouse)

  • Scan all responses, aggregate by group
  • Denormalized, wide tables for fast scans
  • Historical data preserved
  • Multiple sources consolidated
Why not just query the app database? A query scanning 10 million survey responses will lock rows, consume memory, and cause timeouts for users submitting surveys. The performance conflict alone justifies a separate warehouse -- but schema mismatch, historical data needs, and multi-source consolidation make the case even stronger.

Star Schema: The Core Pattern

A star schema has two types of tables: a central fact table storing measurements (things you count, sum, or average) and surrounding dimension tables storing descriptive attributes (the who, what, when, where context). It's called a "star" because the fact table sits at the center with dimensions radiating outward.

The engagement survey framework provides the question dimension -- 12 validated engagement questions grouped into four categories: Basic Needs (Q01-Q02, scores ~3.9-4.1), Individual (Q03-Q06, ~3.4-3.8), Teamwork (Q07-Q10, ~3.0-3.8), and Growth (Q11-Q12, ~3.3-3.5). Each is scored on a 1-5 Likert scale.

Querying the Star: Join, Filter, Aggregate

Every analytical question follows the same pattern: start from the fact table, join the dimensions you need, filter, and aggregate. The star schema makes every combination of slicing available through the same SQL pattern.

-- Mean engagement score for Team Alpha in Q1 2025
SELECT
    dt.team_name,
    dtp.period_label,
    ROUND(AVG(f.score), 2) AS mean_score
FROM fact_survey_responses f
JOIN dim_team dt         ON f.team_key = dt.team_key
JOIN dim_time_period dtp ON f.time_period_key = dtp.time_period_key
WHERE dt.team_name = 'Team Alpha'
  AND dtp.period_label = 'Q1 2025'
GROUP BY dt.team_name, dtp.period_label;

To slice differently -- by question category instead of team -- you join dim_question and group by dq.category. The fact table stays the same; only the joins and groupings change.

Snowflake Schema: When Dimensions Have Dimensions

A snowflake schema normalizes dimension tables further. Instead of dim_team containing department and location directly, those become separate dimension tables linked through foreign keys.

Star vs Snowflake: The Tradeoff

AspectStar SchemaSnowflake Schema
Joins to get department 1 join 2 joins
Query complexity Simpler SQL More joins, harder to debug
Query performance Better (fewer joins) More join overhead
Data redundancy Some duplication Minimal duplication
Update consistency Update many rows Update one row
Deep hierarchies Flat, gets wide Natural fit
In practice, star wins Most data warehouses use star schemas. Disk is cheap, and query simplicity beats storage savings. Snowflake schemas appear when a dimension has deeply nested hierarchies (team -> department -> division -> business_unit -> company) that change independently.
Side-by-Side SQL Comparison (Lab 02)
Star: 1 join to get department
SELECT sdt.department,
       ROUND(AVG(f.score), 2) AS mean_score
FROM star_fact f
JOIN star_dim_team sdt
  ON f.team_key = sdt.team_key
GROUP BY sdt.department
ORDER BY mean_score DESC;
Snowflake: 2 joins to get department
SELECT dd.department_name,
       ROUND(AVG(f.score), 2) AS mean_score
FROM fact_survey_responses f
JOIN dim_team dt
  ON f.team_key = dt.team_key
JOIN dim_department dd
  ON dt.department_key = dd.department_key
GROUP BY dd.department_name
ORDER BY mean_score DESC;

Both return identical results -- Engineering 3.79, Product 3.47, Sales 3.47 -- but the snowflake version requires an extra join hop through dim_team to reach dim_department.

Snowflake Advantage: Division Rollup

Where snowflake shines: querying a parent level in a normalized hierarchy. The division rollup (Technology: 3.68, Revenue: 3.47) is clean in snowflake because division lives on dim_department, its natural home.

Grain: The Critical Design Decision

The grain of a fact table answers: "What does one row represent?" Getting grain wrong is the single most common data warehouse design mistake, and it silently produces wrong numbers.

The average-of-averages trap Team Alpha has 50 responses with avg 4.20, Team Beta has 10 with avg 3.50, and Team Gamma has 30 with avg 3.80. The naive AVG(avg_score) returns 3.83 -- treating all three teams equally. The correct weighted average is 3.99. The difference (0.16 points) can change decisions. The fix: store data at the finest grain. You can always aggregate up; you cannot disaggregate down.

The correct grain for survey data: one row = one person's answer to one question in one time period.

Lab Output: Wrong Grain vs Correct Grain (Lab 05)
Wrong: Average of Averages = 3.83
-- Each team weighted equally
SELECT ROUND(AVG(avg_score), 2)
FROM wrong_grain;
-- Result: 3.83
Correct: Individual Responses = 3.99
-- Each response weighted equally
SELECT ROUND(AVG(score), 2)
FROM correct_grain;
-- Result: 3.99

Measures: Additive, Semi-Additive, Non-Additive

Measures are the numbers you aggregate (score, response_count). Dimensions are the axes you slice by (team_name, category). A useful test: if you'd put it in a GROUP BY, it's a dimension. If you'd wrap it in SUM() or AVG(), it's a measure.

Not all measures can be aggregated the same way across all dimensions:

TypeCan SUM across...ExampleAggregationCorrect?
Additive Any dimension response_count SUM = 90 YES
Semi-Additive Some dimensions mean_score AVG (unweighted) = 3.83 NO
Weighted AVG = 3.99 YES
Non-Additive No dimension p90_score AVG of P90s = 4.50 NO -- must recompute

Additive

SUM works across any dimension. response_count, completion_count. Sum across teams: total responses. Sum across time: total across periods. Always correct.

Semi-Additive

SUM works across some dimensions, not others. mean_score needs a weighted average across groups. Account balances: sum across accounts (total cash), but NOT across time (Jan balance + Feb balance is meaningless).

Non-Additive

Cannot be summed meaningfully. Percentiles, ratios, rates, medians. Team Alpha's P90 is 4.80, Team Beta's is 4.20 -- the overall P90 is NOT (4.80 + 4.20) / 2. Must recompute from raw responses.

This is why grain matters If you store individual responses (finest grain), you can always compute any aggregate correctly -- additive, semi-additive, or non-additive. If you store pre-computed statistics, you're limited to additive operations.

Materialized Views: Pre-Computing Results

A regular view is a saved SQL query -- every read re-executes the underlying SQL. A materialized view stores the query result as a physical table. Subsequent reads scan the stored result instead of re-computing it. The tradeoff: speed vs staleness.

-- Create the materialized view (DuckDB uses CREATE TABLE AS)
CREATE TABLE mv_team_category_scores AS
SELECT dt.team_name,
       dq.category,
       ROUND(AVG(f.score), 2)  AS mean_score,
       COUNT(*)                 AS num_responses
FROM fact_survey_responses f
JOIN dim_team dt     ON f.team_key = dt.team_key
JOIN dim_question dq ON f.question_key = dq.question_key
GROUP BY dt.team_name, dq.category;

Slowly Changing Dimensions (SCD)

Real-world entities change over time. Team Alpha's department changes, an employee moves teams, a question gets reworded. Slowly Changing Dimensions are the patterns for handling these changes in a warehouse.

SCD Type 2: The Essential Pattern

Create a new row for each version of the entity. Each row carries valid_from and valid_to dates. The fact table's foreign key points to the specific version that was active when the event occurred.

All Three SCD Types

TypeMechanismHistoryUse When
Type 1: Overwrite Update the row in place Lost Typo fixes, non-meaningful changes
Type 2: New Row Add row with valid_from/valid_to Full history preserved Restructures, re-orgs -- essential for survey analytics
Type 3: New Column Add previous_value column One level only Rare; only need the immediately prior value

Surrogate vs Natural Keys

A natural key is an identifier from the source system (employee ID, team code). A surrogate key is an auto-incrementing integer the warehouse generates (team_key = 1, 2, 3...). Warehouses prefer surrogate keys for four reasons:

Source Systems Change

If HR renumbers employee IDs, natural keys break. Surrogate keys are warehouse-internal and stable.

Multiple Sources

Two source systems might both have a "Team Alpha" with different IDs. Surrogate keys let you map both without collision.

SCD Support

When Team Alpha restructures, you need two rows in dim_team. A surrogate key gives each version its own identity (team_key 1 vs 2).

Join Performance

Integer joins are faster than string joins. The dimension table keeps both: team_key (surrogate, PK) and team_code (natural, for traceability).

The Survey Data Challenge

Employee engagement survey data is significantly harder to warehouse than classic examples like e-commerce. These challenges exercise every concept on this page.

Dynamic Questions

Questions change every cycle -- added, retired, reworded. Trend analysis ("how has engagement changed over 3 years?") requires mapping old questions to new ones. The dim_question dimension mutates far more than a typical dim_product.

Hierarchical Teams

Teams nest: Team -> Department -> Division -> Company. When Team Alpha moves from Engineering to Product, every level shifts. SCD Type 2 must track changes at every level, and queries must join through the correct hierarchy version for each time period.

Anonymity & Suppression

If Team Gamma has only 3 members, showing their average could identify individuals. Suppression rules hide results for groups below a threshold (typically 5). This cascades -- suppressing one team changes the department rollup.

Pre-Computed Aggregations

Survey platforms often deliver pre-computed results (mean per team per question) rather than raw responses. This creates the grain problem: you're stuck with a coarser grain, and certain calculations (weighted averages, re-slicing by new dimensions) become impossible or incorrect.

Reverse-scored questions "I feel burned out at work" scored 5 (strongly agree) is actually a bad signal. Some questions must be flipped before aggregation. This transformation belongs in the warehouse pipeline, not the reporting layer, because inconsistently applying it produces wrong results.
