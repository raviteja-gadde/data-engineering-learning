What Problem Are We Solving?

Raw data lands in your warehouse from various sources -- survey responses, HR systems, project trackers. The data is messy: duplicate records from retries, inconsistent types, missing values, questions that need reverse-scoring. You need a systematic way to clean, transform, and aggregate so analysts can trust the data.

Two problems, actually:

1. How do you organize transformations?

A giant SQL script that does everything becomes a 500-line monolith nobody can debug. When the reverse-scoring logic changes, you grep through that script and hope you found every place.

Solution: Medallion architecture -- organize into layers with clear guarantees.

2. How do you make them reproducible?

Transformations in a notebook or manual SQL commands mean no version control, no tests, no way to re-run reliably.

Solution: dbt -- version-controlled SQL models with built-in testing. Airflow handles scheduling.

Medallion Architecture: Bronze, Silver, Gold

The medallion architecture organizes your data warehouse into three layers, each with specific guarantees about data quality and shape.

Bronze Layer (Raw Ingestion)

The raw data exactly as it arrived. Nothing is lost, nothing is changed. If the source system sent duplicates, bronze has duplicates. If a score field came in as a string, bronze stores it as a string.

  • Raw CSV/JSON dumps loaded as-is
  • Add metadata: _loaded_at timestamp, _source_file name
  • Never delete, never update -- append only
  • Insurance policy: when a transformation bug corrupts silver, rebuild from bronze

Silver Layer (Cleaned and Conformed)

Cleaned, deduplicated, typed, business-rule-applied data. The "single source of truth" for analysts.

  • Deduplication: ROW_NUMBER() OVER (PARTITION BY response_id ORDER BY submitted_at DESC)
  • Type enforcement: cast score to INTEGER, submitted_at to TIMESTAMP
  • Reverse-scale correction: Q06 is treated as reverse-scored (for demonstration). Raw score 2 becomes 6 - 2 = 4
  • Suppression flags: teams with < 4 respondents are suppressed to protect anonymity
  • Validation: reject rows with scores outside 1-5

Gold Layer (Aggregated, Dashboard-Ready)

Pre-computed aggregates designed for specific analytical use cases. These tables map directly to dashboard widgets.

  • Mean score per team per question category
  • Response rates by department
  • Pre-joined wide tables -- no joins, no aggregations needed by consumers
Where do business rules live? Business rules are encoded in silver models, version-controlled and tested. Reverse-scoring logic, suppression thresholds, deduplication strategy, category mappings -- all live in silver. When the business rule changes, you change one model, the test suite validates it, and the audit trail is a git commit.

What Is dbt?

dbt is make for your data warehouse. make compiles source code into executables by running build commands in dependency order. dbt compiles SQL templates into executable queries and runs them against your warehouse in dependency order.

What dbt Does

  1. You write SQL files (called "models") that define transformations: SELECT ... FROM ... JOIN ... WHERE ...
  2. dbt figures out the dependency order from {{ ref() }} calls between models
  3. dbt runs each model's SQL against the warehouse, creating tables or views
  4. dbt runs tests you defined to validate the results

What dbt Does NOT Do

Not Extract or Load

dbt does not read CSVs from S3, hit APIs, or move data between systems. That is what Fivetran, Airbyte, or custom scripts do.

Not Schedule Itself

It runs when you (or Airflow) tell it to. dbt has no built-in scheduler.

Not Store Data

Your warehouse (DuckDB, Snowflake, BigQuery) stores data. dbt just writes SQL that creates/updates tables in it.

dbt's tagline: "Transform data already in your warehouse." Take that literally. dbt is the T in ELT. It assumes data is already loaded; it handles only transformation.

dbt Project Structure

dbt Core Concepts

Models

A model is a SQL file that defines one transformation. Each file in models/ becomes a table or view in your warehouse. The key insight: the model file contains a SELECT statement, not a CREATE TABLE. dbt wraps it in the appropriate DDL for you.

Bronze model: stg_survey_responses.sql 
-- Bronze: Stage raw survey responses with basic type casting.
-- No dedup, no business rules -- just make the types usable.

select
    response_id,
    respondent_id,
    team_id,
    project_id,
    question_id,
    cast(score as integer)          as score,
    cast(submitted_at as timestamp) as submitted_at
from {{ ref('raw_survey_responses') }}

dbt turns this into CREATE VIEW stg_survey_responses AS (SELECT ...) because bronze is configured as +materialized: view.

Silver model: survey_responses_cleaned.sql (the core transformation) 
-- Silver: Deduplicated, typed, reverse-scale-corrected survey responses.
-- Three things happen here:
-- 1. Dedup: ROW_NUMBER picks the first occurrence of each response_id
-- 2. Reverse-scale: Q06 is treated as reverse-scored for demonstration (raw 5 -> corrected 1)
-- 3. Validation: only scores 1-5 survive

with deduped as (
    select
        *,
        row_number() over (
            partition by response_id
            order by submitted_at desc
        ) as row_num
    from {{ ref('stg_survey_responses') }}
),

unique_responses as (
    select
        r.response_id,
        r.respondent_id,
        r.team_id,
        r.project_id,
        r.question_id,
        r.score       as raw_score,
        r.submitted_at,
        q.is_reverse_scored,
        q.category,
        case
            when q.is_reverse_scored then 6 - r.score
            else r.score
        end as score
    from deduped r
    join {{ ref('stg_question_config') }} q using (question_id)
    where r.row_num = 1
      and r.score between 1 and 5
)

select
    response_id, respondent_id, team_id, project_id,
    question_id, category, raw_score, score,
    is_reverse_scored, submitted_at
from unique_responses

This is the heart of the pipeline. Three operations in one model: dedup via ROW_NUMBER, reverse-scale via CASE WHEN, validation via WHERE score BETWEEN 1 AND 5.

Gold model: team_overview_metrics.sql 
-- Gold: Mean score per team per question category.
-- Joins suppression flags so consumers know which teams can be reported.

select
    r.team_id,
    t.team_name,
    t.department,
    r.category,
    round(avg(r.score), 2)             as mean_score,
    count(*)                           as response_count,
    count(distinct r.respondent_id)    as respondent_count,
    s.is_suppressed
from {{ ref('survey_responses_cleaned') }} r
join {{ ref('team_hierarchy_scd') }}       t using (team_id)
join {{ ref('suppression_flags') }}        s using (team_id)
group by
    r.team_id, t.team_name, t.department,
    r.category, s.is_suppressed

Note the three {{ ref() }} calls: this model depends on survey_responses_cleaned, team_hierarchy_scd, and suppression_flags. dbt knows to build all three before this one.

Seeds

Seeds are CSV files committed to your dbt project. Running dbt seed loads them into the warehouse as tables. Use for small, slowly-changing reference data.

seeds/
  raw_survey_responses.csv   -- 111 rows -> table raw_survey_responses
  raw_question_config.csv    -- 12 rows  -> table raw_question_config
  raw_team_hierarchy.csv     -- 5 rows   -> table raw_team_hierarchy

Refs: The Dependency Graph

{{ ref('model_name') }} does two things: resolves the table name, and declares a dependency. dbt builds a DAG from all ref() calls and runs models in topological order. You never specify the order manually.

Materializations

TypeDDLWhen to UseTradeoff
view CREATE VIEW AS ... Bronze staging. Small transforms. Fast to build, always current. Slow to query on large data.
table CREATE TABLE AS ... Silver, Gold. Most models. Fast to query. Full rebuild on every dbt run.
incremental INSERT INTO ... WHERE new Large fact tables. Append-heavy data. Fast (only new rows). Complex. Needs periodic --full-refresh.
ephemeral Inlined as CTE Simple helper transforms. No table created. Cannot be queried directly.
Incremental models: how they work 
{{ config(materialized='incremental', unique_key='response_id') }}

WITH deduped AS (
    SELECT *, row_number() OVER (
        PARTITION BY response_id ORDER BY submitted_at DESC
    ) AS row_num
    FROM {{ ref('stg_survey_responses') }}

    {% if is_incremental() %}
    WHERE submitted_at > (SELECT max(submitted_at) FROM {{ this }})
    {% endif %}
)
SELECT ... FROM deduped WHERE row_num = 1
  • First run: is_incremental() is false, WHERE clause skipped. Full load.
  • Subsequent runs: only rows newer than the current max timestamp are selected.
  • unique_key: tells dbt to MERGE (upsert) rather than append, preventing duplicates.
The tradeoff: If old data gets corrected in the source, an incremental model won't pick up the correction. You must run dbt run --full-refresh to rebuild from scratch.

Rule of thumb: Start with table, switch to incremental when rebuild time becomes a problem.

The dbt DAG

dbt builds a directed acyclic graph from {{ ref() }} calls. Each node is a model or seed; each edge is a dependency. dbt executes nodes in topological order -- upstream models always finish before downstream ones start.

The dashed arrow from survey_responses_cleaned to suppression_flags shows an intra-layer dependency -- suppression needs the cleaned responses to count respondents per team.

Data Contracts and Testing

Data contracts are formal guarantees about what a model's output looks like. In dbt, you express them through schema.yml tests and custom SQL test files. dbt test runs SQL queries that return failing rows -- zero rows returned means the test passes.

Schema Tests (in schema.yml)

version: 2

models:
  - name: survey_responses_cleaned
    columns:
      - name: response_id
        data_tests:
          - unique         # no duplicate response_ids survived dedup
          - not_null       # every row has a response_id
      - name: score
        data_tests:
          - not_null
          - accepted_values:
              arguments:
                values: [1, 2, 3, 4, 5]   # Likert scale only
                quote: false
      - name: team_id
        data_tests:
          - not_null       # every response has a team
      - name: category
        data_tests:
          - accepted_values:
              arguments:
                values: ['Basic Needs', 'Individual', 'Teamwork', 'Growth']

Test Types

TestWhat It ChecksExample Failure
uniqueNo duplicate values in columnDedup failed, R001 appears twice
not_nullNo NULL valuesA row missing its team_id
accepted_valuesAll values in a known listScore of 7 in a 1-5 scale
relationshipsFK exists in another tablequestion_id 'Q99' not in config

Custom Test: Suppression Logic

-- tests/assert_suppressed_teams_low_count.sql
-- Returns FAILING rows: teams that should be suppressed but aren't.

select
    team_id,
    respondent_count,
    is_suppressed
from {{ ref('suppression_flags') }}
where respondent_count < 4
  and is_suppressed = false

Zero rows returned = the suppression logic is correct. Any rows returned = a team with too few respondents is leaking unsuppressed data.

What a test failure looks like (from Lab 05)

Lab 05 injects a row with score=7 into the silver table, then runs dbt test:

-- Injected: R999, EMP99, T001, Q01, score=7

$ dbt test
  3 of 27 FAIL 1
    accepted_values_survey_responses_cleaned_score__1__2__3__4__5
    Got 1 result, configured to fail if != 0

  Done. PASS=26 WARN=0 ERROR=1 SKIP=0 TOTAL=27

The accepted_values test caught the invalid score. Without this test, the score=7 would have inflated team T001's average in the Gold layer and silently corrupted dashboard numbers.

After rebuilding models from seeds (dbt run), all 27 tests pass again.

Test-driven data quality
  1. Write the test (what SHOULD be true about the data)
  2. Build the model (make it true)
  3. Run tests on every pipeline execution
  4. If tests fail, the pipeline stops -- bad data never ships to dashboards

What Is Airflow?

Airflow is cron that knows about task dependencies and has a monitoring UI. cron can schedule a script to run at 2 AM, but it doesn't retry on failure, doesn't know about dependencies between scripts, and gives you no visibility into what ran or why it failed.

Core Concepts

ConceptWhat It IsExample
DAGA workflow defined in Python. What tasks to run and their dependencies.survey_pipeline, runs daily
TaskA single unit of work within a DAG."Run dbt seed", "Send Slack notification"
OperatorThe type of work a task performs.BashOperator, PythonOperator
ScheduleWhen the DAG runs.@daily, 0 2 * * *
SensorA task that waits for a condition before proceeding."Wait until CSV appears in S3"
ConnectionStored credentials for external systems.Database URL, API key
Two different DAGs: Airflow's DAG is about task scheduling (run dbt seed, then dbt run, then dbt test). dbt's DAG is about SQL model dependencies (build stg_survey_responses before survey_responses_cleaned). They are separate concepts at different levels of abstraction.

A Typical Airflow DAG

from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

dag = DAG(
    'survey_pipeline',
    schedule='@daily',
    start_date=datetime(2025, 1, 1),
    catchup=False
)

extract = BashOperator(
    task_id='extract',
    bash_command='python extract.py',
    dag=dag
)

dbt_seed = BashOperator(
    task_id='dbt_seed',
    bash_command='dbt seed --profiles-dir .',
    dag=dag
)

dbt_run = BashOperator(
    task_id='dbt_run',
    bash_command='dbt run --profiles-dir .',
    dag=dag
)

dbt_test = BashOperator(
    task_id='dbt_test',
    bash_command='dbt test --profiles-dir .',
    dag=dag
)

notify = BashOperator(
    task_id='notify',
    bash_command='python notify.py',
    dag=dag
)

# The >> operator: "runs after"
extract >> dbt_seed >> dbt_run >> dbt_test >> notify

The >> operator means "runs after." Airflow guarantees dbt_run won't start until dbt_seed succeeds. If dbt_test fails, notify doesn't run (or can be configured to send a failure alert instead).

Airflow + dbt Together

The split of responsibilities is clean: dbt owns the transformations, Airflow owns the schedule.

ConcernToolHow
What transformations?dbtSQL model files
In what order?dbtref()-based DAG
Are results correct?dbtData tests (schema.yml + custom SQL)
When does it run?AirflowSchedule (@daily, cron)
What if it fails?AirflowRetry, alerting, failure callbacks
What ran yesterday?AirflowUI, execution logs

Airflow doesn't know or care what dbt does internally. It just runs dbt build as a shell command and checks the exit code. dbt doesn't know or care who invoked it. This separation means you can run dbt locally during development and let Airflow run it in production -- same transformations, different trigger.
