The Agent's Data Access Problem

An AI agent reasoning over analytical data faces a fundamentally different problem than a dashboard. A dashboard renders pixels -- charts, heatmaps, tables. An agent reasons in text. This changes what data access means.

When a user asks "how is my team doing on engagement?", the agent must identify scope, retrieve structured data, interpret it, and compose a response -- all within a single context window. The data must be complete enough to answer without a second round-trip, compact enough to fit alongside the conversation, and annotated enough that the agent can interpret it correctly.

Core Constraint An LLM does not compute -- it pattern-matches over text. The data layer must do the computation (aggregation, trend calculation, benchmark comparison) and hand the agent pre-digested results. The agent's job is interpretation and communication, not arithmetic.

Tool Contracts as Stable Interfaces

The agent accesses data through tools -- typed functions with defined inputs and outputs. The agent never writes SQL, never knows the schema, never connects to a database. This is a hard architectural boundary.

Why the Agent Must Never Touch SQL

  • Security -- prompt injection can produce DROP TABLE or SELECT * FROM salaries
  • Correctness -- EAV pivots, suppression logic, period boundaries are too subtle for ad-hoc SQL
  • Stability -- schema changes break SQL; a tool contract absorbs them internally
  • Testability -- a typed function with defined inputs/outputs is testable; "whatever SQL the LLM wrote" is not

The Tool Contract Dataclass

Error States as Distinct Types

Each failure mode requires a different agent response. Returning generic exceptions or empty results forces the agent to guess.

not_entitled

User lacks permission. Agent says: "You don't have access to that team's results."

suppressed

Group too small (<4 responses). Agent says: "Results are suppressed to protect respondent anonymity."

no_data

No survey responses for this scope. Agent says: "No survey data found for that team and period."

stale_cache

Data older than expected. Agent says: "This data is from last week's refresh."

Scope Resolution

When a user says "how is my team doing?", the agent has a natural language phrase, not a team_id. Scope resolution is the process of converting that intent into the typed parameters the tool contract requires.

Scope Resolution Flow

The key insight: scope resolution is itself a tool contract. get_user_teams() and get_active_projects() are agent tools just like get_team_overview(). A resolve_default_scope() heuristic eliminates the disambiguation step for the common case (user manages exactly one team).

Scope Resolution Dataclasses 
@dataclass
class UserScope:
    user_id: str
    team_id: str
    team_name: str
    project_id: str
    project_name: str
    time_period: str

@dataclass
class TeamMembership:
    team_id: str
    team_name: str
    role: str  # member | manager

def resolve_default_scope(user_id: str) -> UserScope | None:
    """If user manages exactly one team, resolve automatically.
       Returns None if ambiguous -- agent must ask."""
    teams = get_user_teams(user_id)
    managed = [t for t in teams if t.role == "manager"]
    if len(managed) == 1:
        team = managed[0]
    elif len(teams) == 1:
        team = teams[0]
    else:
        return None  # Ambiguous
    project = get_active_projects()[0]  # Most recent
    return UserScope(user_id, team.team_id, team.team_name,
                     project.project_id, project.project_name,
                     project.latest_period)

Caching at the Tool Layer

Same team, same project, same period -- queried twice in one conversation. Should the tool hit the database twice? No. Tool-level caching is a simple dict keyed on the request parameters with a TTL.

Why Cache at the Tool Layer, Not Below

  • Semantic awareness -- the tool layer knows "same team, same period" means the same request
  • Intra-conversation consistency -- if the agent asks about Team Alpha twice, it gets the same numbers both times, even if the source data refreshes between calls
  • Performance -- cache hits return in <1ms vs ~50ms for database queries

Cache Implementation 
@dataclass
class CacheEntry:
    data: dict
    cached_at: float
    hits: int = 0

class ToolCache:
    def __init__(self, ttl_seconds: float = 300):
        self.ttl = ttl_seconds
        self._store: dict[tuple, CacheEntry] = {}

    def get(self, key: tuple) -> dict | None:
        entry = self._store.get(key)
        if entry is None:
            return None
        if time.time() - entry.cached_at > self.ttl:
            del self._store[key]
            return None  # Expired
        entry.hits += 1
        return entry.data

    def put(self, key: tuple, data: dict):
        self._store[key] = CacheEntry(data=data, cached_at=time.time())

The cache key is the scope tuple: (team_id, project_id, time_period). Survey data is batch -- it changes when a new survey closes, not continuously. A 5-minute TTL is more than enough for conversational consistency.

Context Window Constraints

An LLM has a fixed context window. The conversation, system prompt, tool definitions, and tool results all compete for that space. How much room does analytical data actually take?

Context Window Sizing Comparison

The Right Default Shape Flat, complete-for-the-context. For survey data: 4 category scores, 12 question scores, overall score, response count, trend indicators. One level of hierarchy (categories contain questions), no deeper nesting. Past ~3K tokens of tool data, reasoning quality degrades -- the agent starts summarizing rather than analyzing.

Non-Contradiction Requirement

When an agent and a dashboard appear on the same screen, they must show the same numbers. A user who sees "3.85" on the dashboard and the agent says "3.92" will lose trust in both.

How Contradiction Happens

Non-contradiction is an architectural property, not a testing outcome. If two consumers compute independently, they will eventually diverge. The fix is not "run the same SQL" -- it is "read the same pre-computed rows." This is the Gold layer from the medallion architecture (Topic 3) doing its job: compute once, serve everywhere, guarantee consistency.

Try It Yourself Run uv run python labs/09_agentic_data_access/05_non_contradiction.py to see three scenarios: both consumers read the same source (match), a pipeline refresh causes divergence (mismatch), and a shared serving table guarantees consistency regardless of timing.

Lab 02: Scope Resolution -- Three Scenarios

Scenario 1 (Bob -- unambiguous): Bob manages one team (Team Beta). resolve_default_scope("u2") returns a complete UserScope immediately. Zero disambiguation needed.

Scenario 2 (Alice -- ambiguous): Alice is on three teams (Alpha as manager, Beta and Gamma as member). The heuristic picks her managed team, but the lab shows what happens when disambiguation is required: the agent presents all three teams and asks "which one?"

Lab 05: Non-Contradiction -- Three Architecture Scenarios

Scenario 1 (Consistent): Both dashboard and agent read the same PostgreSQL serving table. Both show 3.85. Result: MATCH.

Scenario 2 (Inconsistent): Dashboard reads PostgreSQL at T1 (pre-refresh: 3.85). Agent reads DuckDB at T2 (post-refresh: 3.92). Result: MISMATCH. Delta: 0.07. Both are "correct" but the inconsistency destroys trust.

Scenario 3 (Shared serving): After the pipeline refreshes the Gold table, both dashboard and agent read from it. Both show 3.92. Result: MATCH. Consistent by construction.
